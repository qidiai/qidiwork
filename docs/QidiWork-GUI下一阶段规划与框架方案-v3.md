| 领域 | 当前实际情况 | 下一步要求 |
|---|---|---|
| 任务与会话 | 消息按 session_id 分桶；新建时 office_task 优先复用当前文件分组，否则落默认 QidiWork | 新建任务的唯一归属不能由正在浏览哪个文件分组决定 |

## 三、产品界面框架

### 1. 固定布局

- 左侧：Q 标识、新建任务、最近任务、搜索/归档入口；文件分组浏览作为独立入口，不改变当前执行任务。
- 顶部：任务名称、任务状态、已上报用量与费用；费用未知时显示“尚无统计”，不显示虚构的 0 元。
- 中间：对话、需求确认、执行步骤；详情日志和思考过程默认收起。
- 输入区：资料选择、图片/视频预览、发送/停止；下方常驻模型、思考强度与模型设置入口。
- 右侧：当前任务参考资料、成果文件、保存位置；文件缺失或不能预览给出具体下一步。
- 预览态：文档占主要区域，对话保留；窄窗支持手动收起资料区或预览，不能丢草稿。
- 设置：账号/配额、默认模型、授权与安全、更新/诊断；技术参数保留在高级区域。

### 2. 四类任务共用一个流程

流程：选择目标或直接描述 → 添加资料 → 必要时补充要求 → 开始处理 → 审阅成果 → 继续修改或打开系统程序。

| 类型 | 必要信息 | 第一阶段交付 |
|---|---|---|
| 写文档 | 主题、阅读对象、要点、格式 | 可打开的 Word 文档；缺失事实标注待补充 |
| 整理表格 | 原表、字段/统计目标、计算口径 | 可打开的 Excel 及文字说明；关键数字能复算 |
| 制作汇报 | 汇报对象、主题、重点、页数范围 | 先确认大纲，再生成演示文稿；不承诺当前内嵌 PPT 预览 |
| 审阅标书 | 原文件、检查范围 | 要求清单、缺失项和对应依据；不虚构资质、评分或页码 |

普通写作不强制多轮填表；涉及大量文件改写、批量处理或关键数据缺失时再确认。任务类型只是引导参数，不成为四套重复的执行系统。

## 四、技术框架：保留现有底座

继续使用 **Vue 3 + TypeScript + Tauri v2 + Rust + 单个 ACP 内核进程/多会话**。不引入 Electron、新 Web 服务、第二套 Agent 调度器或为了目录整齐而整体重写。

```text
Vue 展示组件
  任务导航 / 对话与输入 / 模型控制 / 用量 / 文件与预览 / 授权提示
                         │ 用户动作与状态展示
前端状态层
  当前任务选择 + 任务快照
  会话运行态（复用 useAgent）
  附件与草稿态 / 文件展示态 / 设置态
                         │ 白名单命令与带标识的事件
Tauri Rust 服务层
  任务登记与绑定 / 附件与文件访问 / 持久化
  会话与进程生命周期 / 配置与授权 / 用量记录
                         │ 现有 ACP 桥
Agent 内核
  会话、工具执行、模型调用、权限判定、办公技能
                         │
已有数据面
  内核转录 + 成果 manifest + GUI 任务元数据和导入资料
```

职责约束：
1. Vue 只提交意图与展示事实，不决定文件访问许可，不猜测成果归属，不伪造进度。
2. Rust 是任务元数据和本地文件安全访问的唯一写入入口；同一登记文件的读改写串行化，并采用原子落盘。
3. 内核继续负责工具执行和权限判断；界面“完全信任”也只能反映后端真实状态，不能在前端直接跳过弹窗冒充授权。
4. 成果 manifest 保持单写者：沿用技能/card.py 写入、GUI 只读；任务关联元数据不能变成另一套抢写 manifest 的实现。
5. 先固定状态与命令契约，再按职责拆分当前较大的聊天组件；不先大规模拆文件。

## 五、最小数据模型与数据来源

下表为拟议契约，不是当前已存在的数据结构。

| 对象 | 最小字段 | 权威来源 |
|---|---|---|
| Task（办公任务） | task_id、标题、cwd、office_task、active_session_id、归档状态 | Rust 管理的任务登记 |
| Run（一次提交） | run_id、task_id、session_id、状态、开始/结束时间、结果/错误 | Rust 创建提交标识，桥接事件更新 |
| Attachment（附件记录） | attachment_id、task_id、kind、文件名、受控路径或重新选择状态、大小 | Rust 导入记录；前端临时文件不得冒充已落盘 |
| ArtifactRef（成果引用） | task_id、manifest 分组、文件名、受控定位信息、有效性 | 已登记 manifest，经过后端重新校验 |
| UsageRecord（用量记录） | run_id、输入/输出、费用、完整性、收到时间 | 桥接的真实上报；缺值保持未知 |
| EffectiveSettings（生效设置） | 已保存默认值、当前会话模型/强度、已保存授权、实际授权、待生效原因 | 配置文件和内核/桥的当前状态，分别呈现 |

实施选择：
- task_id 由后端在任务建立时生成，标题可改，ID 不变；一任务首期只保留一个活动会话映射，不提前做复杂子任务树。
- 新任务的 office_task 由 task_id 派生，不复用“当前浏览分组”。目录路径只由后端已登记的任务解析，前端不传任意目标路径。
- run_id 在一次提交被受理前生成，内部 Tauri 事件带回同一标识；保持 ACP 标准输入块，不臆造它不存在的协议字段。
- GUI 本地状态先采用小型 JSON 登记和按回合的记录，复用现有原子写方式；当前规模不引入数据库。所有并发修改经过同一服务入口，避免读改写丢数据。
- 未发送文字草稿可自动保存；大体积图片/视频不写入 localStorage。若没有明确保存副本，重启后显示“请重新选择文件”，不显示假附件。
- 视频仅保存必要的采样说明/已发送画面关联；不要因为需要恢复功能而擅自永久保存用户原视频。
- 历史任务不自动搬动或删除文件。旧共享分组保留独立浏览，不能根据相同标题或路径推测归属；需要迁移时先列出映射、备份，再一次性迁移，不维护长期双套写入。

## 六、状态与生命周期框架

把“任务执行状态”“附件准备状态”“成果状态”分开，避免单个 busy 布尔值承载全部含义。

- 附件：待准备 → 准备中 → 就绪；失败/取消保留草稿，重试不得重复导入成功副本。
- 一次执行：排队 → 执行中 ↔ 等待确认 → 回合结束 / 失败 / 已停止；失联进入“状态待恢复”，不直接写成已完成。
- 文件交付：未生成 → 已登记 → 检查可访问 → 可交付；纯问答无需强制有文件，文件任务则必须验证真实产物。
- 归档是列表状态，不等于终止、删除或清理磁盘；运行任务归档前明确是否停止。

必须实现的时序：
1. 新建/发送：创建任务登记 → 建立会话绑定 → 准备附件 → 受理 run_id → 发 prompt → 消费事件 → 核对成果。
2. 切换：切换当前 task_id，其他任务继续按自身标识更新；异步完成回调不得覆盖后来选中的任务。
3. 重启/断线：先读登记和归档状态 → 恢复允许恢复的会话 → 重新查询资料与成果 → 恢复已知设置；中断回合不自动重做可能有副作用的操作。
4. 归档/删除登记：停止或明确保留执行 → 收敛排队/待确认 → 解除恢复清单中的映射 → 清理预览和对象 URL → 更新列表；保留原文件。
5. 永久删除文件：独立动作，列明真实范围，重新校验受控路径并二次确认，不借“删除会话”执行。
6. 用量：同 run_id 的上报重复到达只能记一次；重启回放不重复计费。统计保留本币种，目前美元，不做未经说明的人民币换算。

## 七、授权三档专项

保留新版三档入口，但在扩展之前完成行为核验：
- 分别测试谨慎询问、智能自动、完全信任中的读取、写入、执行、删除请求。
- 区分“新会话读取规则”与“新内核进程读取 permission_mode”。当前前端统一提示“之后启动的会话生效”，与 Rust 明确的两层时机不完全一致，须实测后统一。
- 展示待生效提示；涉及内核重启时显示受影响任务，不自动停止后台正在执行的任务。
- 完全信任必须有明确的影响说明与用户主动确认；此方案不代表授权现在启用它。
- 当前档位写入会替换/移除 allow 规则；存在用户自定义规则时必须先识别并说明影响，不能把“保留 TOML 注释”等同于“保留原授权语义”。
- 不凭按钮名断言权限隔离成立，以内核真实行为和配置前后差异为验收依据。

## 八、分阶段实施与验收

### 阶段 A：合并基线与生命周期收敛（最先做）

范围：补足新会话删除、授权切换、重新连接与附件准备同时发生的回归；统一设置生效提示；建立不丢任务/文件的关闭与恢复语义。

验收：删除列表项后恢复不能无提示复现；准备中关闭任务不会隐形发送；默认模型重启后能恢复原任务而非丢草稿；全局配置变更不静默中断其他任务；原始文件保持不变。

输出：可验证的时序测试与交互说明。未通过前不继续堆功能。

### 阶段 B：唯一任务标识与文件归属

范围：后端统一任务登记；新建任务独立分组；资料、预览、成果查询按 task_id；解决多会话共享默认成果分组的问题。

验收：相同目录中两个任务、同名文件、快速切换、同时生成成果、崩溃恢复均不串内容；旧分组仍可读取，无文件搬移或误删。

### 阶段 C：四类任务的最短交付链

顺序：文档与表格先形成稳定样例，再验证汇报与标书。共用需求确认卡与状态展示，不复制四套后端流程。
