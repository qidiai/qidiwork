# QidiWork 远程接入方案 —— IM 指挥 + 电话语音 + 屏幕共享（v1）

> 2026-09-12 · 状态：方案设计（未实施）
> 目标：在手机上通过**微信 / 飞书 / 企业微信 / QQ / 钉钉**远程给工作台 Agent 下指令、收结果、审批权限；支持**打电话（PSTN 语音通话）**和**屏幕共享**两种更立体的指挥方式。

---

## 1. 背景与目标

工作台当前只能在本机 GUI 里指挥 Agent。真实使用场景里，人经常不在电脑前：通勤路上想让 Agent 跑一个任务、开会时想看进度、Agent 卡在权限申请时需要人批准。本方案回答三个问题：

1. **怎么接**：五大 IM 平台各自如何接入，统一抽象长什么样；
2. **怎么说**：文字之外，语音消息、实时语音、PSTN 电话三种语音路径如何落地；
3. **怎么看**：远程看到 Agent 正在操作的屏幕（单向观察优先，反向控制默认不开放）。

非目标（v1 不做）：多用户多租户、Agent 主动外呼营销类场景、手机反向控制桌面鼠标键盘。

## 2. 现状架构（方案的事实基础）

```
Vue 前端 (gui/src)
   │  Tauri IPC: invoke() / listen(BridgeEvent)        ← useAgent.ts
   ▼
Tauri 壳 (gui/src-tauri)
   │  commands.rs: AgentProcess::spawn + AcpBridge::attach
   │  transport.rs: AgentTransport trait（newline-delimited JSON-RPC 行流）
   │  acp/bridge.rs: ACP ↔ 前端事件桥（含权限请求 permission 状态）
   ▼
内核 qidi.exe (cf-pager-bin, agent 模式) —— ACP over stdio
```

对远程接入友好的三个既有事实：

- **传输层已抽象**：`transport.rs` 明确注释“将来切换 leader(named pipe) 或远程沙箱时提供新的实现即可，协议层不动”。远程网关只是再添一种 transport/前端，内核零改动。
- **ACP 库可复用**：`cf-acp-lib` 已有 `gateway.rs`（AcpGatewayReceiver 消息转发 + meta 分布式追踪）与 `channel.rs`（mpsc 收发对），网关的消息转发骨架不必重写。
- **会话与权限有明确契约**：会话登记簿（`persist.rs`）、权限请求走 ACP permission 流（前端 `PermissionDialog` 消费）。远程审批=把 permission 事件转投 IM 卡片、把用户点按转回 ACP 响应，协议是现成的。

## 3. 设计原则

1. **内核不动**：新增独立进程 `qidi-remote-gateway`（Rust，复用 cf-* crates），经 ACP 与内核通信；GUI 与网关互不阻塞，可同机部署。
2. **安全默认拒绝**（延续本项目审计文化）：通道默认只读；写操作与执行类指令分级授权；权限审批默认超时拒绝；全程审计。
3. **渠道可插拔**：IM 平台差异封装在 Adapter 层，核心层只见统一的 `ChannelEvent` / `ChannelAction`。
4. **公网最小暴露**：优先选平台提供的**长连接 outbound** 模式（飞书 WS / 钉钉 Stream / QQ WS），把“网关必须公网可达”的	req 全部推迟到必须为止。

## 4. 总体架构

```
┌─────────────── 手机端 ───────────────┐
│ 飞书/钉钉/企微/QQ/微信 Bot 会话        │
│ 电话(PSTN)  浏览器 H5(屏幕查看)        │
└──────┬───────────────┬──────────────┘
       │ 平台协议(多数为 outbound WS)   │ WebRTC/WSS
┌──────▼───────────────▼──────────────┐
│        qidi-remote-gateway          │
│  ┌─────────── 接入层 ────────────┐   │
│  │ ChannelAdapter trait:         │   │
│  │  feishu / dingtalk / wecom /  │   │
│  │  qq / wechat / phone / webrtc │   │
│  └───────┬───────────────────────┘   │
│  ┌───────▼───────────────────────┐   │
│  │ 核心: 身份鉴权(白名单)         │   │
│  │  会话路由(IM会话↔Agent会话)     │   │
│  │  指令策略引擎(风险分级)         │   │
│  │  审计日志 + 速率限制            │   │
│  └───────┬───────────────────────┘   │
└──────────┼───────────────────────────┘
           │ ACP（复用 cf-acp-lib gateway/channel）
   ┌───────▼──────────┐     ┌──────────────┐
   │ qidi.exe 内核     │     │ 工作台 GUI    │ ← 本地指挥不受影响
   │ (cf-pager-bin)   │     │ (Tauri 壳)    │
   └──────────────────┘     └──────────────┘
```

**关键决策：网关直连内核（自己 spawn），不经 GUI 进程。**
理由：GUI 关闭时远程仍可用（这是远程指挥的主要价值）；避免跨进程 IPC 先行投入。代价是 GUI 与网关各自 spawn 的内核是两个进程、两份会话登记簿——M2 起引入 named pipe leader 模式（transport.rs 预留的路线）合并为单内核多客户端，届时 GUI 与远程通道看到同一会话流。

### 4.1 会话路由模型

- IM 侧一个「平台用户 + 会话」绑定一个 Agent session（首次绑定时可选拌定到 GUI 里已恢复的会话）。
- 同一时刻同一 Agent session 只允许一个 in-flight prompt（ACP 单 turn 契约）；排队并回执「已排队，当前第 N 位」。
- 长任务中途插入指令：映射为 ACP 的 turn 内消息或 cancel + 新 prompt（策略可配，默认询问）。

### 4.2 统一渠道抽象

```rust
trait ChannelAdapter {
    fn start(&mut self, tx: mpsc::Sender<ChannelEvent>);
    async fn act(&mut self, action: ChannelAction) -> ChannelResult;
}
enum ChannelEvent {   // 渠道 → 网关
    Text { sender_id, channel_id, text },
    Voice { sender_id, channel_id, audio: AudioRef, duration_ms },
    CardClick { sender_id, channel_id, card_id, option_id }, // 权限审批点按
    CallAudioFrame { call_id, pcm },                          // 电话/实时语音
    CallEnded { call_id },
}
enum ChannelAction {  // 网关 → 渠道
    SendText(..), SendCard(..), SendFile(..), SendAudio(..),
    StartFrame, EndFrame, ScreenFrame(..),
}
```

平台差异（卡片语法、文件上传接口、语音格式）全部消化在各自 Adapter 内。

## 5. 五大 IM 平台接入要点与优先级

| 平台 | 接入形态 | 公网要求 | 机器人收语音/文件 | 卡片交互(审批按钮) | 个人可用 | 优先级 |
|---|---|---|---|---|---|---|
| **飞书** | 自建应用 + 事件订阅**长连接 WS** | 否 | ✔ 语音/文件可收发 | ✔ 消息卡片回调 | ✔ | **P0** |
| **钉钉** | 企业内部机器人 + **Stream 模式** | 否 | ✔ | ✔ AI 卡片 | 需企业(可免费建) | **P0** |
| **企业微信** | 自建应用回调(需可信域名) / 智能机器人 | 回调需公网 HTTPS | ✔ | ✔ | 需企业 | P1 |
| **QQ** | QQ 开放平台机器人(q.qq.com) + WS/Webhook | WS 否 / Webhook 是 | 文件弱 | ✔(按钮组件) | ✔(个人开发者可申请) | P1 |
| **微信** | 无个人号官方 API；走 公众号/微信客服/企微互通 | 公众号回调需公网 | 公众号可收语音 | 服务号模板/客服消息受限 | 测试号可玩,正式需资质 | P2 |

各平台落地说明：

- **飞书（首推）**：开放平台创建企业自建应用 → 事件订阅选「使用长连接接收事件」（SDK 内 outbound WS，免公网 IP/免备案）→ 订阅 `im.message.receive_v1`；回复走 `im/v1/messages`，卡片交互走卡片回调。语音消息以 file_key 换取 opus/mp4a 文件。个人可免费创建租户自测。
- **钉钉**：开放平台建企业内部应用 → 机器人 → **Stream 模式**（官方 client，outbound WS，免公网）。AI 卡片支持按钮回调，适合做权限审批卡片。
- **企业微信**：自建应用消息回调要求公网 HTTPS + Token/EncodingAESKey 校验；没有公网时两条路：① 部署到有公网的云中继（见 §9）；② 先用「群机器人 webhook」做**只读通知**（Agent→人单向），指令暂走飞书/钉钉。
- **QQ**：官方机器人平台个人可申请，沙箱群里即可用；注意官方对主动消息有频控与场景限制（群聊 @ 触发为主），适合做轻量通道。
- **微信（最难，P2）**：个人微信号无官方 bot 接口，wechaty/协议号类方案有封号与合规风险，**明确不采用**。正路三条：① 企业微信与微信互通（在微信里加企微联系人/群，消息经企微通道进来）——推荐，等同把微信入口落到企微 Adapter；② 微信客服（企业微信侧开通，有官方 API）；③ 公众号（服务号需企业资质；未认证订阅号 API 残缺）。v1 用 ① 兜底「必须在微信里用」的需求。

## 6. 语音指挥（三条路径）

| 路径 | 链路 | 打断(barge-in) | 成本/复杂度 | 场景 |
|---|---|---|---|---|
| A. IM 语音消息 | 手机发语音 → Adapter 拉文件 → ASR → 文本指令 → 结果回文本/TTS | 无（半双工） | 低 | P0，飞书/钉钉/企微天然支持 |
| B. 工作台本地麦克风 | GUI 录音(可加 WebView SpeechAPI) → ASR → 填入输入框 | 无 | 低 | 电脑前的免打字 |
| C. 实时语音通话 | 电话(PSTN) 或 WebRTC 音频 → 流式 ASR → LLM → 流式 TTS → 回放 | 有（VAD+回声消除） | 高 | P3/P4，打电话场景 |

- **ASR 选型**：云——讯飞/阿里云实时语音（中文效果好、有免费额度）；本地——`whisper.cpp`（small/int4，中文可用，完全离线，契合本项目「安全、数据不出域」偏好）。建议：默认本地 whisper.cpp，云 ASR 做可选后端。
- **TTS 选型**：云（火山/讯飞）保证自然度；本地 fallback 用 Windows SAPI / edge-tts 类方案。
- **指令策略引擎**（路径 A/C 共用）：
  1. ASR 结果先过 **意图分类**（纯提示词实现即可）：查询类（“跑到哪了”）→ 只读答复；指令类（“跑一下测试”）→ 风险分级；审批类（“同意”）→ 校验等待中的 permission 请求；闲聊/无效 → 忽略并回执。
  2. 风险分级沿用权限系统语义：只读直接执行；写文件类回执确认（“回复 确认 执行”）；shell 执行类必须**复述确认**（TTS/文本重复指令内容，等确认词）。
  3. 中文数字/口语容错：ASR 结果与原文一并发给 Agent，由模型兜底纠错。

## 7. 打电话（PSTN 语音通话）接入

**定位**：电话是“找不到任何网络时的兜底入口 + 最自然的主动外呼提醒”，不是主指挥通道。

- **方案 1（推荐）：云语音服务双呼**
  阿里云语音服务 / 腾讯云 TRTC+语音号码：支持「来电接听（呼入 IVR → 转实时 ASR/TTS 会话）」与「外呼（Agent 任务完成/需审批时打给主人，播报并收集口述确认）」。需要企业实名 + 号码实名。网关侧实现一个 `PhoneAdapter`：媒体流对接服务的 ASR/TTS 回调（多数提供 WebSocket 音频流）。
- **方案 2：SIP 自建（FreeSWITCH + 运营商 SIP 中继）**：可控性最强、能完全本地化 ASR/TTS；运维重，M5 之后再评估。
- **方案 3（M1 就可做的降级）**：**外呼通知 + 按键/语音简答**——Agent 卡住/完成时打一通电话播报（TTS），指令细节引导到 IM 完成。只依赖云语音外呼 API，一天可接通。

**通话安全约束**：电话通道默认只允许「查询 + 预授权白名单指令」；执行类一律引导到文字通道二次确认（电话里“同意”这种口头确认只对低风险指令生效，高风险必须文字通道确认，防误听/伪造语音）。

## 8. 屏幕共享 / 远程查看

**用途**：远程看到 Agent 正在操作的工作台画面（观察优先）。反向控制（手机→桌面键鼠）安全面大，默认不开放，列入远期。

- **方案 A（推荐，M5）：WebRTC 推流**
  网关用 Windows Graphics Capture (WGC)/DXGI 采集屏幕 → VP8/H.264 编码 → 经 SFU（自建 LiveKit 单节点，或 Pion 自写 SFU）→ 手机浏览器/小程序 H5 免安装观看。延迟 <500ms，可顺带承载路径 C 的实时语音（同一 PeerConnection），是「打电话 + 看屏幕 + 口头指挥」的最终形态。
- **方案 B（轻量降级，M2 可做）：差帧截图推送**
  网关低频（1~2fps、变化帧才发）截取工作台窗口 → JPEG → 以 IM 文件/卡片推送。无需任何流媒体设施，先满足“瞄一眼”需求；注意截图经第三方服务器，涉敏内容用户可配「仅局域网可看」。
- **隐私与开关**：共享必须显式开启（GUI 设置页 + 远程口令双重确认）；提供「遮挡模式」（仅采集工作台窗口而非全屏，WGC 支持窗口级采集）。

## 9. 安全设计（硬性要求）

1. **身份**：每通道维护发送者白名单（平台 user_id/open_id 精确匹配）；陌生人私信一律忽略并审计。网关与云中继间 TLS；网关本地监听仅 127.0.0.1。
2. **配对**：手机与网关首次绑定为「GUI 显示 6 位配对码 → IM 里输入」双人确认，防平台账号被盗后直接操控。
3. **指令风险分级**（§6 策略引擎）：只读 / 写 / 执行三档，执行档默认要求文字通道复述确认；电话通道见 §7 约束。
4. **权限审批远程化**：ACP permission 请求转 IM 卡片时，卡片必须回显完整命令与路径；按钮点击校验请求 ID 新鲜度（默认 5 分钟超时 = 拒绝）；可选「高危仅限桌面审批」开关。
5. **审计**：网关记录全部进出消息（时间、平台、发送者、指令、结果摘要、审批链路），本地文件 + 可选上报；沿用 `cf-secrets` 管理平台 token，日志脱敏。
6. **公网暴露最小化**：飞书/钉钉长连接模式网关可完全不出公网；必须公网时（企微回调/WebRTC）走云中继小盒子（frps 或轻量 VPS 反代），中继与网关 mTLS 互认，禁止 0.0.0.0 裸端口（延续此前审计对 0.0.0.0 绑定的整改结论）。
7. **速率与爆炸半径**：每通道 prompt 速率限制；网关侧保留「紧急停止」指令（`stop`，映射 ACP cancel），单次风险操作前自动快照（复用 git worktree 能力）。

## 10. 分期路线

| 里程碑 | 内容 | 验收 |
|---|---|---|
| **M1** | 网关骨架 + 飞书 Adapter（长连接）+ 只读查询类指令 + 外呼通知（方案 3） | 手机飞书发“状态”能拿到 Agent 进度；任务卡住能接到电话 |
| **M2** | 指令下发（含风险分级）+ 权限远程审批卡片 + 企微 webhook 通知 + 差帧截图 | 手机上能派活、能在卡片上批准权限申请 |
| **M3** | 钉钉/QQ/企微 Adapter 齐活；IM 语音消息 ASR；TTS 回复（可配） | 五平台均可文字指挥，三家可发语音 |
| **M4** | named pipe leader 共享内核（GUI 与远程同会话）+ 云 ASR/TTS 后端 | GUI 与手机看到同一会话流 |
| **M5** | PSTN 双呼（方案 1）+ WebRTC 屏幕共享 + 实时语音（打断） | 打电话指挥 + 手机看屏幕 |

工作量粗估：M1≈1 周（飞书 SDK + 网关复用 cf-acp-lib）；M2≈1~2 周（审批卡片与安全联调占大头）；M3 每平台 2~4 天；M4≈1 周；M5≈2~3 周（含云服务开通与实名流程，**建议 M1 期间并行启动资质申请**）。

## 11. 开放问题

1. 微信入口最终形态（企微互通 vs 微信客服）取决于用户企业资质情况，M2 前确认。
2. 电话通道 ASR/TTS 的云厂商需实名与号码备案，走个人还是企业主体待定。
3. 云中继部署形态（VPS frps vs 云函数）与费用，M2 前定。
4. 屏幕共享若需在小程序内嵌（而非 H5），受小程序 live-pusher/player 域名白名单限制，可能影响方案 A 的端上选型。
