# 方案：根治「安装包误带 CLI 二进制」——CLI 拆独立 crate

**日期**：2026-11-16
**触发**：codely-core 审计阻断——安装包出现未声明的 `bid_export.exe`，且 `"externalBin": []` 也关不掉。
**目标**：让 GUI 安装包**只含应用本体 + 内核 + 模板**；CLI 成为独立可分发物；两者模板解析都不再靠"猜目录"。

---

## 1. 事实基线（已实测）

| 事实 | 证据 |
|---|---|
| 打包会带上 `bid_export.exe`（1.9 MB） | `target/release/nsis/x64/installer.nsi:646-647` |
| 干净重建（删 `nsis/`+`bundle/`）两次均复现 | 2026-11-16 21:14 / 21:27 两次构建 |
| 显式 `"externalBin": []` 无效 | 同上，21:27 构建仍含该文件 |
| 其余 5 个 bin 未被打包（bid_import/pages/project/smoke/gen_bid_template） | `grep` NSI 仅命中 bid_export |
| `qidiwork.exe`（132 MB 内核）是**有意**随包 | `src/process/mod.rs:38-43` 按 `<resource_dir>/qidiwork.exe` spawn |
| CLI 模板默认路径是开发态路径 | `paths::resolve_from` 的 dev 回退用 `CARGO_MANIFEST_DIR`；装到 Program Files 后该路径不存在 |

**结论**：同包多 bin 时，Tauri 的"主二进制/外部二进制"判定不可控且无配置出口；把 CLI 留在 GUI 包里，无论修不修模板路径，都是"未声明行为"。根治只能让 GUI 包**只剩一个 bin**。

---

## 2. 候选方案

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A 拆 crate** | 新建 workspace 成员 `gui/cli`（crate `qidiwork-cli`），把 6 个 bin 迁过去，依赖 `qidiwork-gui` 库 | GUI 包只剩主 bin，问题根除；CLI 可单独发版；职责清晰 | 一次迁移成本；文档命令要改 | **推荐** |
| B feature gate | 6 个 bin 加 `[[bin]] required-features=["cli"]`，cli 不进 default | 不动目录结构 | 开发/CI 每条命令都要 `--features cli`；Tauri 构建是否传 `--no-default-features` 不可控，仍有被打包风险 | 不推荐 |
| C 正式随包 | 承认 CLI 是产品一部分，修好安装态模板解析 | 少改动，用户可在安装目录直接跑 CLI | 仍然只有 `bid_export` 一个被"随机"带上，其余 5 个没有；行为依旧不可解释 | 仅作 A 的过渡 |
| D 构建后剔除 | `beforeBundleCommand` 删除 `target/release/bid_export.exe` | 一行脚本 | 依赖 Tauri 钩子时序，脆弱；治标 | 不采用 |

## 3. 方案 A 施工设计

### 3.1 落地结构（实际形态）

```
gui/
  src-tauri/                 # workspace root；crate qidiwork-gui（库 + 唯一 bin: qidiwork-gui）
    Cargo.toml               # [workspace] members = ["cli"]
    src/main.rs
    src/office/bid/...       # 引擎与全部单测（不动）
    cli/                     # 新 crate qidiwork-cli（6 个 bin），位于 root 之下
      Cargo.toml             # [dependencies] qidiwork-gui = { path = ".." }
      src/bin/{bid_export,bid_import,bid_pages,bid_project,bid_smoke,gen_bid_template}.rs
```

**为什么不是草案里的 `gui/cli/`**：cargo 要求 workspace member 必须位于 workspace root 之下。
本 workspace root 是 `gui/src-tauri`，所以 `gui/cli` 这种"root 的同级目录"只能靠
`members = ["../cli"]` 登记，而**指向 root 之外（上级目录）的 member 路径会被 cargo 拒绝**——
`gui/cli` + `members = ["../cli"]` 实测不通过。故落地上提为 root 的子目录 `gui/src-tauri/cli`
+ `members = ["cli"]`：crate 名、bin 名、依赖方向、行为全不受影响，只是物理位置下移一层。

`gui/src-tauri/Cargo.toml`：
```toml
[workspace]
members = ["cli"]          # 根包自动是成员，不要再写 "."（codely-core 审计）
```
根 `G:\qidiwork/Cargo.toml` 增加 `exclude = ["gui"]`，防止将来 path 依赖把 GUI 拉进根工作区；同时修正 `gui/src-tauri/Cargo.toml:11` 里"根已 exclude 本目录"的**不实注释**。

**与草案一致、未变的部分**：6 个 bin 名称不变；crate 名 `qidiwork-cli`、版本 `0.1.11` 与 GUI 同步；
依赖方向仍是 CLI → GUI lib（`qidiwork-gui = { path = ".." }`），GUI 包不反向依赖 CLI。

### 3.2 迁移步骤

1. 新建 `gui/src-tauri/cli/Cargo.toml`（`name = "qidiwork-cli"`，`edition 2024`，依赖 `qidiwork-gui` path + `serde`/`serde_json`；**不引新依赖**）。
2. `git mv` 6 个文件：`src/bin/*.rs` → `cli/src/bin/`。
3. 修正 import：bin 里若有 `use qidiwork_gui::...` 保持；若用到 crate 内私有项，改为 `pub` 导出（预期只有 `paths::probe_resolve` 已 pub）。
4. **模板解析改造**（红线：**所有 `CARGO_MANIFEST_DIR` 用法必须留在 lib**）：
   - `paths` 增加两个函数（均在 lib，宏在 lib 内展开恒为 `gui/src-tauri`）：
     - `pub fn resolve_for_exe(style_id: &str) -> Result<(PathBuf, &'static str), String>`：先 `current_exe` 同级 `templates/<id>.docx`（source=`resource`），再 lib 的 `resources/templates/<id>.docx`（source=`dev`）。
     - `pub fn dev_templates_dir() -> PathBuf`：lib 的 `CARGO_MANIFEST_DIR/resources/templates`。
   - bin 内**禁止**再写 `env!("CARGO_MANIFEST_DIR")`；需迁移的已知调用点：`bid_export.rs:89`、`bid_smoke.rs:88`、`gen_bid_template.rs:34`。
   - CLI 默认模板改用 `resolve_for_exe`（打印 source）；`--template` 显式指定优先。
   - GUI 内 `resolve_template_path(app, …)` 不变。
5. `gen_bid_template` 无参输出改走 `paths::dev_templates_dir()`；**不要再做"exe 同级可写就写那里"**的推断（开发态 exe 同级目录恒可写，会把模板写到 `gui/src-tauri/cli` 下）。无参行为必须仍落 `gui/src-tauri/resources/templates/`。
6. 删除 `src-tauri/Cargo.toml` 里的 `[[bin]]`/`default-run` 之外的 CLI 相关残留（`[[bin]]` 保留主 bin 声明）。
7. 文档与脚本全面改命令：`cargo run -p qidiwork-cli --bin bid_export -- …`。**同步全集**（grep 实测）：
   - `docs/ops/{bid-export-cli,bid-project,bid-import,bid-packaging}.md`
   - **`gui/tests/bid-export/golden.sh`**（跑 `cargo run --bin bid_smoke/bid_export`，不改必断）
   - `gui/src-tauri/Cargo.toml:11` 陈旧注释
   - 历史文档（`docs/施工规格-*`、`docs/审计-*`）**不回改**，属记录。

### 3.3 验收标准

| # | 项 | 判据 |
|---|---|---|
| 1 | GUI 包只含 4 类文件 | 安装后目录 = `qidiwork-gui.exe` + `qidiwork.exe`(内核) + `templates\` + `uninstall.exe`；**无** `bid_*.exe` |
| 2 | NSI 无外部二进制条目 | `grep -c "bid_" installer.nsi` == **0**；`Copy/Delete external binaries` 段落头可存在但必须为空（实测 Tauri 固定输出空段落头） |
| 3 | 库测试不退化 | `cargo test --lib office::bid` == 94 passed |
| 4 | CLI 可用 | `cargo run -p qidiwork-cli --bin bid_export -- --md …` → EXPORT OK；`bid_pages` 同；`cargo metadata --manifest-path gui/src-tauri/cli/Cargo.toml` 通过且 qidiwork-gui targets 只剩 1 个 bin |
| 5 | CLI 安装态可解析模板 | CLI 产物与 `templates/` 同目录 → 导出成功且打印 `source=resource` |
| 6 | 前端不回归 | `npm run build` 通过 |
| 7 | 打包可复现 | 干净重建两次：`grep` 判据均 0；NSIS 两次的**载荷文件清单与各自大小一致**（`7z l -slt` 或安装后 `dir` 对比）。**不再要求 sha256 一致**——PE/NSIS 含时间戳，两次构建注定字节不同 |

### 3.4 风险与缓解

| 风险 | 缓解 |
|---|---|
| `qidiwork-gui` 作为 bin+lib 被 CLI 依赖，可能触发 tauri 的 build 逻辑 | CLI 只依赖 lib target；`cargo build -p qidiwork-cli` 不会跑 `tauri_build` 的打包步骤（build.rs 只生成元数据） |
| 迁移后路径类测试依赖 `CARGO_MANIFEST_DIR` 指向变化 | 单测全在 lib 内，`CARGO_MANIFEST_DIR` 仍是 `gui/src-tauri`，不变 |
| 发布链要同时发 GUI 与 CLI 两个产物 | `prod/releases` 分开命名：`qidiwork-setup-x.y.z.exe` 与 `qidiwork-cli-x.y.z-win64.zip` |
| 迁移期双份代码 | 用 `git mv` 一次性移动，禁止复制；同 commit 内改完 |

### 3.5 回滚

单 commit 可回滚：`git revert <sha>` 即恢复 bin 在 GUI crate 内（安装包回到"多一个 bid_export.exe"的旧状态，不影响功能）。

### 3.6 工作量

约 **2.5–3 小时**（迁移 40 分钟 + 模板解析与调用点改造 40 分钟 + 脚本/文档同步 30 分钟 + 两次干净打包与验收 40 分钟）。

---

## 4. 不在本方案内

- 内核 `qidiwork.exe` 的版本校验（另立小项：打包前 `--version` 比对）；
- 代码签名；
- CLI 的独立安装包（先出 zip，签名后再做 installer）。
