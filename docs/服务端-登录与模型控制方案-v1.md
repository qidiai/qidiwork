# QIDI 服务端：登录与模型控制方案 v1.1

> 日期：2026-09-19 · 状态：v1.1 已按代码交叉审计修订（审计存档：qidiwork-docs/审计-2026-09-19-服务端登录与模型控制方案-代码交叉审计.md）
> 目标：用户注册/登录后，由我们的服务器统一控制"谁能用哪些模型、用多少、走哪个上游"，并实现 Qoder 式 `auto` 模型路由。
>
> **v1.1 修订摘要**：①认证端点全部改为 `/oauth2/*`（客户端硬编码，B1）；②补 OIDC Discovery + JWKS + id_token 验签要求（B2）；③`/v1/models` 字段改 `name` 并补 `context_window`（B3）；④BYOK 强制点更正为服务端 JWT-only（W1）；⑤补遗漏端点容错（W2）与 models 拉取认证分叉说明（W3）；⑥删除不可实现的 `session_turns` 特征（W4）；⑦scope 白名单与 id_token claims 约束（W5/W6）；⑧P0 排期与 free 档配额调整。

## 0. 代码现状盘点（本方案的可行性基础）

调研 `cf-shell/src/auth` 与 `cf-shell/src/agent/config.rs` 后确认，客户端**已具备完整的参数化能力**，不需要动核心逻辑：

| 能力 | 现成开关 | 说明 |
|---|---|---|
| OAuth2/OIDC issuer + client_id | 环境变量 `QIDI_OAUTH2_ISSUER` / `QIDI_OAUTH2_CLIENT_ID`，或 config.toml `[grok_com_config.oauth2]` / `[grok_com_config.oidc]` | `auth/config.rs:227-249` `from_env()`；x.ai 默认值只是 fallback（`config.rs:273-280`） |
| 设备码登录（RFC 8628） | `auth/device_code.rs` 已实现 | 服务端照协议出接口即可 |
| 授权码 + PKCE 回环登录 | `auth/flow.rs`、`oidc/` | 同上 |
| 推理网关 base_url | `QIDI_CLI_CHAT_PROXY_BASE_URL`（`agent/config.rs:581`） | 客户端实际调用 `/v1/chat/completions`（OpenAI 兼容） |
| 模型目录下发 | `QIDI_MODELS_BASE_URL` / `QIDI_MODELS_LIST_URL` → `GET {base}/models`（`config.rs:566-575`） | **动态模型列表是现成功能**，服务端换目录客户端零改动 |
| 外部认证提供者 | `QIDI_AUTH_PROVIDER_COMMAND`（stdout 出 token） | P0 兜底路径：先不接 OAuth，用一个本地命令换 JWT |
| API key 登录禁用 | `QIDI_DISABLE_API_KEY_AUTH` | ⚠️ 审计更正（W1）：只对 `*.x.ai` 域生效，管不住自建网关；BYOK 强制点在服务端 JWT-only，见 §7.6 |

**客户端唯一需要改的硬编码点**：`auth/config.rs:133` 的 CORS 允许源 `https://accounts.x.ai`（授权页向本地回环端口投递 code 用）。自建账号页域名 `accounts.qidiai.ltd`（或 `api.qidiai.ltd`）必须加进 `PROD_ACCOUNTS_APP_ORIGINS`，否则回环登录收不到 code。注意 `config.rs:380` 有 FROZEN 契约测试，改常量需同步改测试断言。

**结论：本方案 80% 的工作量在服务端，客户端只做"换默认值 + CORS 白名单 + GUI 登录入口"三件小事。**

## 1. 总体架构

```
┌─ 客户端（QIDI Code / QidiWork GUI）
│   · 登录：设备码 / 浏览器回环（OAuth 2.1 + PKCE）→ 拿 access JWT(15min) + refresh token(30d)
│   · 推理：所有请求 → https://api.qidiai.ltd/v1/...   Authorization: Bearer <JWT>
│   · 真实上游 API key 永不下发到用户机器
│
└─ 服务端（部署在 111.231.166.204，nginx 反代 + certbot，复用 qidi-limits 限流区）
    api.qidiai.ltd
    ├── /oauth/*        认证服务（设备码 + PKCE + token 刷新）
    ├── /v1/models      模型目录（按用户套餐裁剪）
    ├── /v1/chat/completions   推理网关（验token→查权益→路由→转发→流式回传→记账）
    ├── /v1/user        账户信息 / 剩余配额（GUI 展示）
    └── 数据层：SQLite（起步）→ 需要时迁 Postgres
```

服务端技术栈：**FastAPI + SQLite + httpx（流式转发）**。理由：服务器上 8765 选股服务已验证 Python 栈稳定可跑；SSE 透传实现简单；后续加队列/统计生态齐全。不用 Rust axum 是为了和内核解耦——服务端迭代速度优先。

## 2. API 契约

### 2.1 认证 `/oauth2/*`（路径为客户端硬编码，不可改）

**设备码（CLI 无浏览器场景 / SSH 远程）** — 照 RFC 8628，端点路径来自 `device_code.rs:142,220`：

```
POST /oauth2/device/code
  req:  { client_id, scope }
  resp: { device_code, user_code:"ABCD-1234", verification_uri:"https://api.qidiai.ltd/activate",
          expires_in:600, interval:5 }        # 与客户端常量吻合，勿改

POST /oauth2/token
  req:  grant_type=urn:ietf:params:oauth:grant-type:device_code&device_code=...&client_id=...
  resp: { access_token, refresh_token, expires_in:900, token_type:"Bearer", id_token }
  err:  { error:"authorization_pending" | "slow_down" | "expired_token" }
```

**浏览器回环（GUI / 本地 CLI）**：OAuth 2.1 Authorization Code + PKCE，**discovery 驱动**——客户端先拉
`GET /.well-known/openid-configuration`（issuer 下标准路径），服务端必须提供：

```
{ "issuer":"https://api.qidiai.ltd",
  "authorization_endpoint":"https://api.qidiai.ltd/oauth2/authorize",
  "token_endpoint":"https://api.qidiai.ltd/oauth2/token",
  "jwks_uri":"https://api.qidiai.ltd/oauth2/jwks", ... }
```

- 授权页 `https://api.qidiai.ltd/authorize`（微信扫码或邮箱密码登录），回调 `http://127.0.0.1:<port>/callback`；
- **`id_token` 必须是 RS256 签名的 JWT，客户端会用 `jwks_uri` 公钥验签**（`auth/oidc/`），验不过直接登录失败；服务端启动时生成 RSA 密钥对即可；
- **`id_token` claims 必须含 `sub` 与 `email`**，否则 CLI 显示 unknown 用户（W6）；
- **授权端点必须照单全收客户端 FROZEN 的 8 个 scope**：`openid profile email offline_access grok-cli:access api:access conversations:read conversations:write`（`config.rs:388` 冻结测试），未实现的 scope 记为"已授予但暂无语义"即可（W5）。

**JWT claims**（access token）：
```json
{ "sub":"<user_id>", "plan":"free|pro", "scope":"api:access", "iat":..., "exp":... }
```
refresh token 存库可撤销（`/oauth2/revoke`，GUI 加"退出所有设备"）。

### 2.2 模型目录 `GET /v1/models`（字段名对齐客户端解析）

```json
{ "object":"list", "data":[
  { "id":"auto",      "object":"model", "owned_by":"qidi", "name":"Auto（智能选择）", "context_window":200000, "default":true,  "min_plan":"free" },
  { "id":"qidi-fast", "object":"model", "owned_by":"qidi", "name":"快速模型",          "context_window":200000, "cost":1, "min_plan":"free" },
  { "id":"qidi-pro",  "object":"model", "owned_by":"qidi", "name":"强力模型",          "context_window":200000, "cost":3, "min_plan":"pro"  }
]}
```
- 字段名是 **`name`**（非 display_name）与 **`context_window`**——后者不下发时客户端一律按 256,000 处理（`tools/config.rs:216` 等多处），会带偏 auto-compaction 阈值与路由的 ctx_ratio 计算，**必须如实下发**；
- 目录存 DB（`model_catalog` 表），后台改表即生效，**不发客户端版本**；
- 响应带 `Cache-Control: no-cache`；客户端 `/model` 菜单与 `--model` 校验都以此为准；
- **认证分叉注意（W3）**：客户端设了 `QIDI_MODELS_BASE_URL` 时拉目录会优先带 `XAI_API_KEY`；因此 C3 只烘焙 chat proxy 默认值，models 目录走 Session token 模式，避免用户机器上有残留 key 时行为分叉。

### 2.3 推理网关 `POST /v1/chat/completions`

请求体与 OpenAI 格式一致（客户端已按此发出）。网关处理链：

```
① 验 JWT（过期→401，客户端已有 refresh 流程自动续）
② 查权益：model ∈ 用户 plan 可见集？否→403 {error:{code:"plan_required"}}
③ 查配额：当日请求数 / token 预算未超限？否→429 {error:{code:"quota_exceeded"}, reset_at}
④ 路由：model=="auto" → 路由引擎选真实模型（见 §3）；显式模型 → 查映射表
⑤ 换 key：用服务器侧上游凭证重写请求，转发到真实上游（流式 SSE 透传）
⑥ 记账：从最后一个 usage chunk 提取 prompt/completion tokens，写 usage_log
⑦ 响应头附带：X-Request-Id、X-Quota-Remaining、X-Model-Resolved（auto 实际选了谁）
```

### 2.4 用户信息 `GET /v1/user`

```json
{ "id":"u_...", "email":"...", "plan":"free", "plan_expires":null,
  "usage_today": { "requests":42, "tokens":183000 },
  "quota":       { "requests_left":8,  "tokens_left":817000 } }
```
GUI 设置页/状态栏直接渲染。

### 2.5 附带端点容错（W2，P0 集成测试必测）

客户端除三大端点外还会自动打以下地址（均基于 proxy base 拼接），服务端必须**返回 404/403 或最小合法响应而非 5xx**，并验证客户端能优雅降级：
- `GET {proxy}/deployment/config`（远程配置拉取，`agent/config.rs:342`）
- OTLP trace 上传（feedback/telemetry 通道）
- `POST {proxy}/feedback` 类端点（`feedback_base_url` 默认跟 proxy）

P0 决策：`/deployment/config` 返回 `{}`；telemetry/feedback 直接 404，客户端仅记 warn 日志不阻塞。

## 3. `auto` 路由引擎（核心设计）

路由 = **规则表 + 特征打分 + 兜底链**，全部在服务器执行，客户端只发 `model:"auto"`。

### 3.1 请求特征（网关侧提取，无需客户端上报）
- `msg_len`：messages 总字符数；`ctx_ratio`：占所选模型上下文窗口的比例
- `has_tools`：请求带 tools 定义（agent 工具调用 → 必须选函数调用能力强的模型）
- `has_code_block` / `zh_ratio`：内容形态

> v1 中的 `session_turns` 特征已删除（W4）：OpenAI 兼容请求体里没有 session_id，且本设计声明网关无状态。若 P1 需要会话维度特征，走客户端加 `X-Session-Id` 请求头的扩展，不在 P0。

### 3.2 路由规则（DB 表 `routing_rules`，热更新）
```
优先级  条件                                        选择              备注
100     has_tools && ctx_ratio>0.3                  upstream_strong   agent+长上下文→旗舰
 90     has_tools                                   upstream_mid      工具调用是硬门槛
 80     ctx_ratio>0.5                               upstream_long     纯长文→大窗口模型
 70     msg_len<400 && !has_tools                   upstream_cheap    短问答→最便宜
 50     默认                                        upstream_mid
```
每条规则命中后落到"候选模型组"，组内再按 **权重 × 成本系数 × 健康度** 排序。权重就是调控旋钮：上游打折/有免费额度时调权重即可挪流量。

### 3.3 兜底链与熔断
- 每个候选配 fallback 顺序：`strong → mid → cheap`；
- 上游 429/5xx/超时（首字节 >15s）→ 立即切换下一候选重试（仅未发出任何 chunk 时可安全重试）；
- 连续 5 次失败 → 该上游熔断 60s，健康度降级，路由自动避开；
- 全链失败 → 502 `{error:{code:"upstream_exhausted"}}`，客户端已有重试语义。

### 3.4 与内核已有机制的边界
内核自带 auto-compaction/上下文阈值逻辑（`cf-agent`），路由只看**请求入参**，不依赖客户端状态——保持服务端无状态假设，将来加 Redis 也只是缓存。

## 4. 数据模型（SQLite 起步）

```sql
users(id, email, password_hash NULL, wechat_openid NULL, plan, plan_expires_at, created_at)
refresh_tokens(token_hash, user_id, device_name, expires_at, revoked_at)
model_catalog(model_id, display_name, min_plan, cost, visible, sort)
upstreams(id, base_url, api_key_enc, model_real, weight, enabled)
routing_rules(priority, condition_json, candidate_group)
quotas(user_id, day, requests_used, tokens_used, requests_limit, tokens_limit)  -- UPSERT 记账
usage_log(ts, user_id, model_requested, model_resolved, prompt_tokens, completion_tokens, latency_ms, status)
```
配额默认值（审计建议）：free = 100 请求/日 + **50 万 token/日**，且路由 cost 上限锁 1（不落旗舰档）；pro 档后台可调。nginx 层已有 `qidi_api 10r/s`、`qidi_login 1r/s` 限流区直接复用，防爆破。

## 6. 分期计划

**P0（先跑通身份，4-5 天；若砍回环登录只做设备码可压回 2-3 天）**
- 服务端：FastAPI 骨架 + `/oauth2/*`（设备码 + discovery/JWKS + token 刷新）+ JWT 签发/撤销 + users/refresh_tokens 表；
- 网关先**透传单上游**（我们现有某一家 key 放进服务器），路由/配额只做最简版（放行+记账）；
- §2.5 附带端点容错全量验证；
- 客户端：C1/C2/C3 + `login` 走通自建 issuer；
- 验收：新用户从 CLI 登录（设备码路径）→ 终端显示已登录 → 对话经网关成功，`usage_log` 有记录；回环登录（GUI 路径）含 id_token 验签通过。
- **排期说明（审计建议）**：完整回环流必须带 discovery + JWKS + RS256 验签，工作量大于 v1 预估；如需 2-3 天交付，P0 只做设备码 + `auth_provider_command` 兜底，回环挪 P1。

**P1（控制面成型，~3 天）**
- `/v1/models` 目录裁剪 + 客户端菜单动态化验证；
- auto 路由表 + 多上游 + 兜底链 + 熔断；
- 配额强制（429）+ `/v1/user` + GUI 配额展示；
- 后台管理：改目录/改规则/封号的最小 CLI 或网页。

**P2（商业化，另立方案）**
- 套餐/支付、按 token 计费、多设备管理、用量报表；
- cf-update 端点参数化（更新通道已定案 qidiai.ltd，与本服务共用 api 子域或发布子站均可）。

## 7. 安全红线（评审时逐条确认）

1. 上游真实 key 只存服务器（env/加密列），任何响应与日志不得回显；
2. JWT 15 分钟 + refresh 30 天可撤销；登录接口走 `qidi_login 1r/s` 限流；
3. 网关对请求体大小设上限（如 2MB），防内存放大；
4. usage_log 不落 prompt 原文（只落长度与哈希），合规且省磁盘——服务器磁盘已用 73%；
5. 全站 HTTPS，api 子域走 certbot webroot 自动续期（与现有子站同套路）;
6. **BYOK 管控的真实手段（W1 更正）**：`QIDI_DISABLE_API_KEY_AUTH` 只对 `*.x.ai` 域生效，**管不住自建网关**——若不允许用户绕过，强制点必须在服务端：网关只接受自家 JWT（无 JWT / 非本服务签发 → 401），BYOK 用户则用客户端本地覆盖 base_url 直连上游（无法从根上禁止，只能不在默认配置里提供）。P1 前维持"允许 BYOK"现状。

## 8. 开放问题（请你拍板）

1. **注册方式优先级**：邮箱+密码先行，微信扫码放 P1？还是首发就要微信（需公众号/开放平台资质，个人主体扫码登录受限）？
2. **free 档配额数值**：审计建议 **50 万 token/日**（v1 的 100 万偏慷慨），并按 plan 限制路由 cost 上限（否则 free 用户 agent 场景全落旗舰档，成本算不住）。
3. **BYOK 去留**：见 §7.6——技术上无法从根上禁止本地覆盖 base_url，只能控制默认配置。建议明确"允许 BYOK 作为高级选项"。
4. 上游第一家接谁：决定 P0 的 key 成本与 `/v1/models` 初始目录。
5. **P0 范围**：4-5 天含回环登录，还是 2-3 天只做设备码（回环挪 P1）？
